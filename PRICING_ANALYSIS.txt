    (This is the absolute floor — every credit used for a full 30-min lecture.)

    Scenario A — 30-min lectures (1 credit each):

      Margin: 68.5%  ← PROFIT

    Scenario B — 90-min lectures (3 credits each):
      5 lectures × 90 min = 450 min; cost $3.15; revenue $9.99

  The 25-hr cap is a security backstop, not expected to be hit under honest usage.
  Removing the 20-import/month cap has no margin impact — credits are the real gate.

      Mitigation: 4-hr per-session cap + credit checks eliminate this scenario.

               = 20 lectures × 4 hours = 80 hours = 4,800 minutes

  PLAN:        PRO ($19.99/month)

  MONTHLY CAP: 2,400 min (40 hrs) — this user would hit it after 10 lectures

  Credits needed: 20 lectures × ceil(240/30) = 20 × 8 = 160 credits
  Monthly time hit: 10 lectures × 240 min = 2,400 min = MONTHLY CAP → stops here

    - Lectures 11–20: BLOCKED by the 40-hr monthly ceiling
    Credits used for 10 lectures: 10 × 8 = 80 credits
    Plan gives 30 credits → 50 credits must be purchased

    Our API cost: 10 × 240 min × $0.007 = $16.80

    Our profit:   $41.98 - $16.80 = $25.18  (59.9% margin)

    No. The 40-hr/month ceiling stops them at 10 sessions.
    They cannot buy their way past the time ceiling — it is enforced by plan limits.
    This is intentional: the time cap protects server capacity and prevents abuse.

  RESULT: Even the most aggressive realistic Pro user generates $25.18/month profit.

7. SECURITY MITIGATIONS (all implemented)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. MULTI-ACCOUNT CREDIT FARMING [MITIGATED]
     Risk: Users create multiple free accounts to farm 5 starter credits each.
     Max loss per fake account: $1.05 (5 credits × $0.21).
     Mitigations applied:
       a) email must be non-empty in JWT — blocks anonymous/no-email signups
       b) email_verified = true required — extracted from Clerk JWT; blocks
          users who signed up with an unverified disposable email
       c) DB partial unique index on credit_transactions (user_id) WHERE
          reason = 'starter_grant' — migration 005_starter_grant_unique.sql
       d) Code try/except catches any race that slips past the app-level check

     Remaining gap: CAPTCHA on signup (handled by Clerk config, not code).
     Add Clerk's Bot Protection in the Clerk dashboard for full coverage.

     MANUAL ACTION REQUIRED: Run migration in Supabase SQL editor before launch:
       backend/migrations/005_starter_grant_unique.sql

  2. IP-BASED RATE LIMITING BYPASS [FIXED]
     Risk: X-Forwarded-For header can be spoofed to bypass per-IP rate limits.
     Fix: rate_limit.py now uses a hybrid key function:
       - Authenticated requests → keyed on user_id (extracted from JWT sub claim)
       - Anonymous requests → keyed on remote IP (fallback)
     Result: Spoofing the IP header has zero effect for logged-in users.

  3. RACE CONDITION IN STARTER GRANT [FIXED]
     Risk: Two simultaneous /credits/balance calls could double-grant credits.
     Fix: maybe_grant_starter() now wraps the INSERT in try/except; the DB
     partial unique index (item 1c above) ensures only one succeeds.

  4. REFUND USES WRONG AMOUNT [FIXED]
     Bug: refund_credit() always refunded 1 credit regardless of lecture cost.
     Fix: now fetches total_duration_seconds from the lecture row and calls
     credits_for_duration(duration) to refund the exact amount deducted.

  5. PRO PLAN NO-SESSION-CAP [FIXED]
     Previously live_max_duration_seconds = None (unlimited).
     Now fixed to 14,400s (4 hrs) to prevent unbounded API calls in one session.

8. OUT-OF-CREDITS UX (HTTP 402 handling — implemented)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  The "out of credits" moment mid-month is the single highest-conversion touchpoint.
  A user who just ran out of credits has already seen value and wants more. Showing a
  generic error throws that moment away. We show a purpose-built conversion UI instead.

  BACKEND (endpoints.py):
    When credit check fails, returns HTTP 402 with:
      { "error": "no_credits", "credits": <balance>, "required": <needed> }
    This applies to: POST /live/start, POST /transcribe, POST /ask, POST /explain

  FRONTEND — Live session (App.jsx):
    402 on live/start → dedicated "Out of credits" modal (not a generic error banner).
    Shows:
      - "Out of credits" heading
      - "This lecture needs N credits. You have M."
      - "1 credit = up to 30 min · 4-hr lecture = 8 credits" hint
      - "Buy credits →" button  → navigates to /credits page
      - "Cancel" button
    Context: user was about to start a live session. The modal keeps them on the page
    and routes them directly to purchase instead of losing them to a dead end.

  FRONTEND — Import modal (ImportModal.jsx):
    402 on /transcribe → inline amber "Not enough credits" card inside the modal.
    Shows:
      - "Not enough credits" heading (amber color scheme — attention, not error red)
      - "This import needs N credits. You have M."
      - "1 credit = up to 30 min · 2-hr lecture = 4 credits" hint
      - "Buy credits →" button → closes modal, navigates to /credits
    Context: user had already selected a file. The card appears inside the existing
    modal so they see their file is still there if they come back after buying credits.
    Amber (warning) rather than red (error) — "you need more" not "something broke."

  WHY THIS MATTERS FOR REVENUE:
    Users who hit the credit wall are your highest-intent buyers.
    Generic error: most users give up and leave.
    Purpose-built UX: direct path to /credits page with context ("you need N credits")
    = measurably higher conversion at zero additional cost.
